### — ChatGPT·Claude·코딩 하네스는 한 번의 명령을 어떻게 처리하고, 무엇을 자동화하며, 어떻게 효율적으로 도는가

## 초록 (Abstract)

현대 에이전트형 어시스턴트(ChatGPT/o-시리즈, Claude/Claude Code, 그리고 유사 하네스)는 표면적 다양성에도 불구하고 **하나의 동일한 아키텍처로 수렴**한다: **LLM은 상태 없는(stateless) 의사결정자**로서 구조화된 *툴 호출 요청*을 내보낼 뿐 **스스로 아무것도 실행하지 않으며**, 그 주위의 **결정론적 런타임("하네스")**이 while-루프를 돌리고, 툴을 실행하고, 결과를 되돌려 넣고, 컨텍스트를 관리하고, 가드레일을 강제한다. 정전적(canonical) 루프는 ReAct이며, 툴 사용은 JSON 스키마 함수 정의로 규율되고, 효율은 **프롬프트 캐싱**(접두사 KV 재사용; 지연 ~80%·입력비용 ~90% 절감)과 **병렬 툴 호출**에 크게 의존한다. 가장 명확히 문서화된 **자동화 경계**는: *모델은 툴 선택·계획·종합을 자동화하고, 하네스는 루프·실행·재시도·상태·컨텍스트 오버플로를 결정론적으로 스캐폴딩한다.*

## 1. 서론: "모델"과 "하네스"의 분리

사용자가 한 번 명령("이 폴더 분석해서 보고서 써")을 내리면, 겉보기엔 AI가 파일을 읽고, 이미지를 보고, 웹을 뒤지고, 여러 단계를 거쳐 답을 낸다. 그러나 그 내부에서 "AI"가 하는 일과 "프로그램"이 하는 일은 **선명하게 갈린다.**

- **LLM(모델)**: 입력 토큰열을 받아 다음 토큰을 예측하는 순수 함수에 가깝다. **상태가 없다** — 이전 대화는 매 턴 통째로 다시 입력으로 들어간다 [검증]. 모델은 "툴을 쓰겠다"는 *의도*와 그 *인자(JSON)*를 텍스트로 내보낼 뿐이다.
- **하네스(런타임)**: 모델의 출력을 파싱해 실제로 파일을 읽고, HTTP를 치고, 셸을 실행하고, 결과를 다시 모델 입력에 끼워 넣는 결정론적 루프. 권한·재시도·타임아웃·상태 저장·컨텍스트 압축이 전부 여기 산다.

이 글의 중심 테제는 **"에이전트 = 상태 없는 모델 + 결정론적 하네스의 폐루프"**이며, 이는 Anthropic·OpenAI의 1차 문서가 거의 동일한 언어로 확인한다(§5).

## 2. 핵심 에이전트 루프 (Perceive → Reason → Act → Observe)

### 2.1 ReAct: 추론과 행동의 인터리빙
정전적 패턴은 **ReAct**(Yao et al., 2022)다. 모델이 **추론 흔적(reasoning trace)과 행동(action)을 번갈아** 생성하여, 추론은 계획을 유도·추적·갱신하고 예외를 처리하며, 행동은 외부 소스(지식베이스·환경)와 상호작용해 정보를 모은다 [검증, arXiv:2210.03629]. 핵심 효용은 **환각(hallucination)·오류 전파 감소**다(인간 라벨링: CoT 오탐률 14% vs ReAct 6%) [검증].

> **정직한 단서(2-1 분할표결).** "ReAct가 항상 더 정확하다"는 **틀린 일반화**다. HotpotQA에서 ReAct *단독*(27.4 EM)은 CoT(29.4)·CoT-SC(33.4)보다 **낮고**, 결합(ReAct→CoT-SC=35.1)에서야 최상위가 된다. 줄어드는 것은 **환각**이지 정확도 순위가 아니다. ReAct 원어휘는 Thought→Action→Observation(3수)이며 "perception"은 후속 문헌의 일반화다.

### 2.2 Reflection / 자기비평
**Reflexion**(Shinn et al., 2023)은 **가중치 갱신 없이 언어적 피드백**으로 개선한다: 피드백을 *언어로 반성*해 **에피소드 메모리 버퍼**에 저장, 같은 과제의 다음 시도에서 의사결정을 개선한다 [검증, arXiv:2303.11366]. 오늘날 "self-critique / reflect-and-retry"의 원형.

### 2.3 루프의 형태와 종료 — 가장 구체적인 1차 문서
Anthropic 문서는 클라이언트측 루프를 **`stop_reason`에 키를 둔 while-루프**로 명문화한다 [검증, Anthropic tool-use docs]: 툴과 함께 요청 → Claude가 `stop_reason:"tool_use"` + `tool_use` 블록 응답 → 앱이 각 툴 실행 후 `tool_result`로 재전송 → **`tool_use`인 동안 반복**. 종료는 **`end_turn`/`max_tokens`/`stop_sequence`/`refusal`** [검증]. (서버측 루프는 `pause_turn`·`model_context_window_exceeded` 추가.)

### 2.4 학습된 툴 사용이라는 대안: Toolformer·MRKL
**Toolformer**(Schick et al., 2023)는 *어떤 API를·언제·어떤 인자로* 호출하고 결과를 다음 토큰 예측에 통합할지를 자기지도로 학습, 호출·결과를 특수 토큰으로 인라인 삽입한다(API당 시연 몇 개) [검증, arXiv:2302.04761]. 그 선조 **MRKL**(AI21, 2022): LLM을 이산 지식·추론 모듈과 결합해 전문가로 라우팅하는 **뉴로-심볼릭** 구조 — *규모 확장만으론 한계(최신·독점정보·추론·모델폭발)를 못 넘는다* [검증, arXiv:2205.00445]. ReAct는 MRKL-영감으로 자기규정.

> **요지**: 상용 ChatGPT/Claude는 *주로* 하네스-오케스트레이션형(ReAct/MRKL). Toolformer형 내재화는 대안으로 존재하나 주축 아님.

## 3. 툴 사용 메커니즘 (파일·이미지·웹·코드를 "쓰겠다"는 결정)

### 3.1 함수/툴 호출 프로토콜 — JSON 스키마 계약
OpenAI 1차 문서의 **5단계 흐름** [검증, OpenAI function-calling]: 툴과 함께 요청 → 모델이 *툴 호출* 반환 → **개발자 코드가 함수 실행**(모델 아님) → 결과 반환 → 최종 응답(또는 추가 호출). *"함수 호출은 실행이 아니라 응답 포맷"*. 툴은 **JSON 스키마**(`type`/`name`/`description`/`parameters`/`strict`)로 기술되며, "파일을 읽을지/이미지를 볼지/웹 검색할지"의 결정은 **모델이** 스키마+맥락을 보고 내려 해당 `tool_use`/function-call 블록을 방출한다. **모델은 구현을 절대 못 보고 스키마와 결과만 본다** [검증, Anthropic].

### 3.2 병렬 툴 호출
모델은 **한 턴에 여러 툴 호출**을 방출할 수 있다(병렬); `parallel_tool_calls=false`로 턴당 1개로 강제 [검증, OpenAI]. (단서: o-시리즈는 순차; 내장 툴과 병렬 불가.) — "파일 여러 개 동시 읽기"의 메커니즘.

### 3.3 구조화 출력 / 제약 디코딩
`strict=true`는 함수 인자가 JSON 스키마를 **보장**하게 한다(Structured Outputs/제약 샘플링; `additionalProperties:false`·전속성 `required` 요구) [검증, OpenAI]. (단서: 안전거부·절단·병렬과 비호환은 예외.)

### 3.4 이미지·파일·웹·코드 — 누가 무엇을 [일부 검증/추론]
- **파일**: 모델이 `read_file` 호출 → 하네스가 디스크에서 읽어 주입.
- **이미지(비전)**: 멀티모달 모델이 이미지를 **입력 토큰**(패치 임베딩)으로 직접 추론(별도 "실행" 아님); *가져오는* 행위는 하네스. 내부 파이프라인은 비공개 [추론].
- **웹/코드**: Claude의 `web_search`·`code_execution` 등 **서버측 툴**도 *서버가 실행* — **모델은 어떤 경우에도 실행 안 함**(실행 주체는 클라이언트 앱 또는 서버 인프라) [검증, Anthropic].

## 4. 컨텍스트 & 메모리 관리

### 4.1 선형 누적과 무상태성
LLM은 상태가 없어 **모든 이전 메시지가 통째 보존·매 턴 재전송**(입력=전체 히스토리+현재); 성장은 **선형** [검증, Anthropic context-windows]. (단서: 확장사고 블록은 모델별 제거; 챗 UI는 rolling FIFO; opt-in 압축.)

> **투명성(기각).** *"실효 컨텍스트=(입력−이전 사고토큰)+현재 턴"* 공식은 적대 검증 **0-3 기각** — 사실로 제시 금지.

### 4.2 프롬프트/KV 캐싱 — 효율의 핵심
양 벤더 동일 메커니즘 **접두사 매칭**: 접두사가 캐시됐으면 KV 재사용, 아니면 처리 후 캐시 [검증]. **OpenAI**: ≥1024토큰 **자동**(코드 0), 정확 접두사만 히트(첫 ~256 해싱, 128토큰 증분). **Anthropic**: `cache_control` 중단점(≤4), 접두사 해시, 100% 동일만 히트, 순서 **tools→system→messages**, **기본 TTL 5분**(사용 시 무료 갱신), 1시간 옵션 [검증]. **수치**: 지연 **~80–85%↓**, 입력비용 **~90%↓**(캐시 토큰 ~10% 과금) [검증, 양 벤더]. (단서: 벤더 최선값; OpenAI 자동=50% 할인, 90%는 설정 의존; TTL 기본 2026-03경 1h→5m 변경.)

### 4.3 컨텍스트 인식·오버플로 — 모델/플랫폼 협업
**컨텍스트 인식**(Sonnet 4.6/4.5, Haiku 4.5): 시작 시 `<budget>` 주입, 매 툴 호출 후 `<system_warning>Token usage: X/Y; Z remaining</system_warning>` → 모델이 잔여를 추적·관리 [검증]. **오버플로**: **서버측 compaction(beta)**가 1차 — 자동 요약; 그 외 context editing(tool-result/thinking-block clearing). 메커니즘은 결정론(임계치 감지→요약→compaction 블록→계속) [검증, Anthropic]. (요약 *내용*은 모델, *메커니즘*은 플랫폼 — §5 경계의 구체 사례.)

### 4.4 장기 메모리·다중 세션·서브에이전트 [보강: 1차 소스 직접 인용]
- **MemGPT/Letta** [1차, arXiv:2310.08560]: OS의 계층적 메모리에서 영감받은 **virtual context management**. 두 계층 — **빠른 메모리**(LLM의 한정된 컨텍스트 윈도) vs **느린 메모리**(외부/아카이벌 저장: 대화 이력·문서). **LLM 스스로 함수 호출로 메모리를 관리** — 요약·성찰을 영구 저장에 기록, 아카이브에서 과거 검색, interrupt로 자기/사용자 제어 흐름 조절. 결과: 컨텍스트 윈도를 "훨씬 초과하는" 문서 분석 + 장기 상호작용으로 기억·성찰·진화하는 대화 에이전트.
- **다중 에이전트 fan-out/fan-in** [1차, Anthropic "multi-agent research system"]: **오케스트레이터-워커** — 리드 에이전트가 작업을 분해해 **각자 독립 컨텍스트 윈도를 가진 서브에이전트를 병렬 spawn**(병렬 탐색이 곧 컨텍스트 압축), 리드가 결과 종합(fan-in). **비용**: 에이전트는 챗 대비 **~4×**, 멀티에이전트는 **~15× 토큰**. **이득**: 내부 리서치 평가에서 단일 Opus 4 대비 **+90.2%**(폭넓은 병렬 탐색 과제). **약점**: 공유 컨텍스트·강한 상호의존 과제(대부분의 코딩)엔 불리 — 진짜 병렬화 가능한 작업이 적음. *(이 문서를 만든 딥리서치 워크플로가 정확히 이 패턴 — 단, 합성 단계에서 한 번 크래시.)*

## 5. 자동화 경계 — "AI가 하는 일 vs 프로그램이 하는 일"

문서로 확인된 경계 [검증, 양 벤더]:

| 구분 | **모델(LLM)이 자동화** | **하네스/런타임이 결정론적 스캐폴딩** |
|---|---|---|
| 의사결정 | 툴 **선택**·계획·인자 생성·최종 **종합** | — |
| 실행 | (없음 — 절대 실행 안 함) | 툴 실행(파일/HTTP/셸/코드), 결과 주입 |
| 제어 흐름 | (다음 행동 *제안*) | while-루프, `stop_reason` 분기, **종료 판정** |
| 신뢰성 | — | 재시도·타임아웃·에러 핸들링 |
| 안전 | (거부 가능) | 권한/가드레일·허용목록·샌드박스 |
| 상태 | (상태 없음) | 세션·히스토리 저장·스케줄링 |
| 컨텍스트 | 예산 인식·요약 *내용* | 오버플로 *감지·압축·치환* 메커니즘 |

*"모델은 스스로 아무것도 실행하지 않는다 — 구조화 요청을 방출하면 코드(또는 서버)가 수행하고 결과가 대화로 흘러든다"* [검증, Anthropic]; *"개발자 코드가 함수를 실행하지 모델이 아니다"* [검증, OpenAI]. **두 벤더의 독립적 일치**가 보편성의 강한 증거. (단, 재시도·권한·스케줄링 *세부*는 핵심 API 문서가 아니라 에이전트 SDK 문서에 — 미해결.)

## 6. 효율 기법

### 6.1 검증된 핵심: 프롬프트 캐싱 + 병렬 호출
에이전트 루프는 거대·*안정적* 접두사(시스템·툴 정의·히스토리)를 매 턴 재전송 → **접두사 KV 캐싱이 최대 효율 레버**(지연 ~80%·비용 ~90%↓) [검증]. 병렬 툴 호출은 독립 I/O를 묶어 왕복↓ [검증].

### 6.2 추가 효율 기법 [보강: 1차 소스 직접 인용]
- **Speculative decoding** [1차, arXiv:2211.17192]: 작은 *근사/초안* 모델이 여러 토큰을 제안하면 큰 *타깃* 모델이 **한 번의 forward로 병렬 검증**. 핵심 보장: **출력 분포가 타깃 모델과 동일**(exact decoding, "without changing the distribution") — 품질 손실 0. T5-XXL에서 **2–3× 가속**(출력 동일).
- **모델 라우팅/캐스케이드 (FrugalGPT)** [1차, arXiv:2305.05176]: **LLM 캐스케이드**(싼 모델부터, 품질 점검 실패 시에만 비싼 모델로 escalate) + prompt adaptation + approximation. **GPT-4 성능을 최대 98% 비용 절감**으로 매칭(또는 동일 비용에 정확도 +4%). → 오늘날 "Auto" 모델선택·소형/대형 분기의 토대.
- **PagedAttention / vLLM** [1차, arXiv:2309.06180]: OS 가상메모리·페이징 영감 — **KV 캐시를 블록 단위 페이징**해 낭비 거의 0 + 요청 내·간 KV 공유. 동일 지연에서 FasterTransformer·Orca 대비 **처리량 2–4×**(긴 시퀀스·큰 모델일수록↑).
- **연속 배칭·스트리밍·early-exit** [추론 — 권위 1차 문서 미확보, 신뢰도 중].

## 7. 최신 연구 트렌드 2024–2026 [보강: 1차 소스 직접 인용]
- **에이전트 평가의 현실화 — SWE-bench** [1차, arXiv:2310.06770]: 12개 Python 레포의 **실제 GitHub 이슈 2,294건**을 코드 편집으로 해결(레포 테스트 통과가 채점). 출시 시점 최고 모델 **Claude 2가 1.96%**만 해결 — "정답 텍스트"가 아니라 "과제 실제 완수"로의 전환을 상징(이후 에이전트 하네스로 비율 급상승 — 버전 민감).
- **τ-bench / τ²-bench** [배경, Sierra; arXiv:2406.12045]: 에이전트 ↔ **시뮬레이션 사용자 + 도메인 정책 + 툴** 대화 평가. **pass^k**(k회 독립 시행 일관성)로 측정 → 프런티어 에이전트의 *신뢰성/일관성 부족*을 드러냄. *(이번엔 직접 재페치하지 못함 — 신뢰도 중.)*
- **Test-time compute / 추론 모델** [1차, Snell et al., arXiv:2408.03314]: **추론 시 연산을 난이도에 맞춰 최적 배분**하면 모델 파라미터 확장보다 효율적. best-of-N 대비 **>4× 효율**, 비자명한 기저 성공률 문제에선 작은 모델+테스트타임 연산이 **14× 큰 모델을 능가**(FLOPs 매칭). → o-시리즈·확장 사고의 이론적 근거.
- **Agentic RAG**: 검색을 1회 전처리가 아니라 *루프 안의 툴*로(반복 검색·재질의) [배경].
- **장문 컨텍스트 vs 외부 메모리**: 100만 토큰 윈도 ↔ MemGPT류 외부 메모리·compaction의 상호보완 [§4.4 참조].
- **다중 에이전트 시스템**: §4.4 참조 — 오케스트레이터-워커, 단일 대비 +90.2%, ~15× 토큰.
